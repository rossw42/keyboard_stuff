# QMK to VIAL Porting Scripts

A collection of Python scripts for converting QMK keyboards to VIAL-enabled format, based on analysis of **504 keyboards** across **130+ manufacturers**. See `Research Foundation` section below.

---

## Overview

This directory contains two specialized scripts for different conversion workflows:

| Script | Purpose |
|--------|---------|
| `qmk_to_vial_porting.py` | Full porting coordinator - generates all VIAL files (vial.json, config.h, rules.mk, keymap.c, README.md) |
| `keyboard_to_vial_converter_precise.py` | Standalone vial.json generator - matches real vial-qmk format exactly |

---

## Script 1: qmk_to_vial_porting.py

Complete automation system for converting any QMK keyboard directory to VIAL-enabled format.

### Usage

```bash
python qmk_to_vial_porting.py "keyboards/boston"
# Optional: specify output directory as positional argument
python qmk_to_vial_porting.py "keyboards/boston" "output_dir"
```

### What It Generates

For each keyboard, the script creates a `keymaps/vial/` directory containing:

1. **vial.json** - Generated by `keyboard_to_vial_converter_precise.py`
2. **config.h** - Hardware configuration based on detected processor and RGB type
3. **rules.mk** - Build flags with VIAL/VIA enabled
4. **keymap.c** - Copied from `keymaps/default/keymap.c` or minimal default created
5. **README.md** - Build documentation

### Detection Capabilities

The script automatically detects:
- **Processor Type**: ARM or AVR from `keyboard.json.cpu`
- **RGB Configuration**: Underglow (WS2812), backlight (keycap lighting), or none
- **Keyboard Layout**: Split, USB-only, or standard

## Script 2: keyboard_to_vial_converter_precise.py

Standalone converter that generates vial.json files matching the real vial-qmk format exactly.

### Usage

```bash
python keyboard_to_vial_converter_precise.py "keyboards/boston/keyboard.json"
```

### Output Format

The converter follows these patterns discovered from analyzing real vial.json files:

- **Position markers** use ONLY `{"x": N}` (y field omitted for standard keys)
- **Wide keys** stored as SEPARATE `{"w": N}` entries followed by coordinate string
- **Coordinate strings** are PLAIN strings like `"row,col"`

### Example Output Structure

```json
{
  "name": "keyboard_name",
  "vendorId": "0xXXXX",
  "productId": "0xXXXX",
  "lighting": "qmk_rgblight",
  "matrix": {"rows": 6, "cols": 12},
  "layouts": {
    "keymap": [
      {"x": 0}, "0,0",
      {"x": 1}, "0,1",
      {"w": 2, "x": 0.5}, "3,5",
      ...
    ]
  }
}
```

## Porting Workflow (qmk_to_vial_porting.py)

### Step 1: Hardware Detection

The coordinator automatically detects:
- **Processor Type**: ARM or AVR from `keyboard.json.cpu`
- **RGB Configuration**: Underglow, backlight, or none
- **Keyboard Layout**: Split, USB-only, or standard

### Step 2: vial.json Generation

Uses `keyboard_to_vial_converter_precise.py` internally to generate proper format.

### Step 3: config.h Creation

Selects template based on hardware:

**Minimal ARM (no RGB):**
```c
#define VIAL_KEYBOARD_UID {0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00}
#define VIAL_UNLOCK_COMBO_ROWS { 0, X }
#define VIAL_UNLOCK_COMBO_COLS { 0, Y }
```

**RGB Underglow (WS2812):**
```c
#define WS2812_DI_PIN D2
#define RGBLED_NUM 16
#define RGBLIGHT_VALUER(R) ((R) >> 5)
#define RGBLIGHT_EFFECT_BREATHING
#define RGBLIGHT_EFFECT_RAINBOW_MOOD
#define RGBLIGHT_EFFECT_SNAKE
```

**RGB Backlight (keycap lighting):**
```c
#define RGBLED_NUM 1
#define RGBLIGHT_HUE_STEP 8
#define RGBLIGHT_SAT_STEP 16
```

**AVR Processor (special handling):**
```c
#if defined(__AVR_ATmega32U4__)
    #undef LOCKING_SUPPORT_ENABLE
    #undef LOCKING_RESYNC_ENABLE
    #undef RGBLED_R_PIN
    #undef RGBLED_G_PIN
    #undef RGBLED_B_PIN
    // ... all RGB effects undefined
#endif
```

### Step 4: rules.mk Creation

Generates VIAL enablement flags with optional feature toggles:

```makefile
VIA_ENABLE = yes
VIAL_ENABLE = yes
LTO_ENABLE = yes
QMK_SETTINGS = no
CAPS_WORD_ENABLE = no
LAYER_LOCK_ENABLE = no
REPEAT_KEY_ENABLE = no
RGBLIGHT_ENABLE = yes  # For RGB-enabled keyboards
```

### Step 5: keymap.c Setup

Copies from `keymaps/default/keymap.c` or creates minimal default.

## Output Directory Structure

After conversion, the output directory contains:

```
<keyboard_name>/keymaps/vial/
├── vial.json           # VIAL layout definition (generated by precise converter)
├── config.h            # Hardware configuration (template based on hardware)
├── rules.mk            # Build flags (VIA/VIAL enabled)
├── keymap.c            # Key mappings (copied from default)
└── README.md           # Build documentation
```

## Edge Cases Handled

| Case | Handling |
|------|----------|
| AVR Processor | Undefines unsupported RGB effects in config.h |
| RGB Underglow | Sets WS2812_DI_PIN and RGBLED_NUM in config.h |
| RGB Backlight | Enables RGBLIGHT_ENABLE in rules.mk |
| Split Keyboard | Adds combos/unlock_combos to vial.json |
| USB-Only Mode | Sets usbOnly: true, null VID/PID |
| No keyboard.json layouts | Uses empty keymap array (minimal output) |

## Research Foundation

The conversion system is built on comprehensive analysis of **504 keyboards** across **130+ manufacturers**, revealing critical patterns in how QMK's `keyboard.json` maps to VIAL's `vial.json` format.

### Key Discoveries from 504 Keyboard Analysis

#### Coordinate System Patterns
- **Float Coordinates** (Boston, Arisu, split designs): Uses float x values like `x=0.5`, `x=1.75`, `x=3.25` for wide/off-center keys
- **Integer Coordinates** (Alpha, Canton, standard layouts): Uses integer column indices (`x=0`, `x=1`, `x=2`)
- **Plain String Format**: Some keyboards use simple `"r,c"` strings without wrapper when no coordinate fields exist

#### Wide Key Detection Rules
- The `w` property in keyboard.json consistently maps to explicit wide key flags in vial.json
- Float x values (like `x=0.5`) indicate centered/wide keys; integer x values indicate standard keys
- Wide keys may use separate `{"w": N}` entries or combined wrapper with w property

#### Row Structure Types Identified
1. **Single Entry Per Row** (~60% of entries): Standard keys with `[{"x": N, "y": M}, "r,c"]` format
2. **Multi-Key Rows**: Complex layouts like Boston use position markers as separators between key regions
3. **Wide Keys with w Property**: Explicit `{"w": 2}` entries for physical wide/centered keys
4. **Complex Rows with Metadata**: Color and property entries separated into individual objects

#### Matrix Coordinate Mapping Rules
- keyboard.json's `"matrix": ["row", "col"]` directly maps to vial.json coordinate strings
- x/y fields in keyboard.json become wrapper objects `[{"x": N}, "r,c"]` in vial.json
- y field is often omitted when all keys default to same row (common optimization)

#### What Gets Preserved vs Stripped
**Always Preserved:**
- Layout keymap structure and coordinate values
- Float x/y position values for wide/offset keys
- Wide key `w` property

**Conditionally Preserved:**
- Color properties (only if present in original vial.json source)
- Encoder pin data (requires special handling)
- RGB matrix settings (may be simplified)

**Stripped During Conversion:**
- Switch keycode numbers (VIA metadata separates config from keycodes)
- Modifier arrays (VIA handles hotkey rules differently)
- Full encoder pin array (simplified or stripped)
- Complete keys dictionary (only essential properties preserved)

#### Multi-Layout Handling
- When keyboard.json has multiple layouts as a dictionary, only the first/default layout is extracted
- Complex multi-layout keyboards are simplified to default layout only for vial.json output
